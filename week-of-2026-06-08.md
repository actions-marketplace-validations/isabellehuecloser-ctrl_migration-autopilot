## 💼 LinkedIn FR (déjà prérempli dans launch.ics — juste Publier)

Une migration qui a tourné en 0,4 seconde sur staging a locké notre table users en prod pendant 20 minutes.

La ligne, c'étaient trois tokens. ALTER COLUMN ... SET NOT NULL. Staging avait 30 000 lignes. La prod en avait plus d'un milliard. Postgres a scanné chaque ligne pour valider la contrainte, en tenant un lock exclusif tout du long. Pendant 20 minutes, l'app a renvoyé des 503 à tout le monde.

Le fix est connu. Le pattern est dans tous les handbooks Postgres. Mais rien dans le flux de PR review standard ne signalait "cette commande va bloquer les writes le temps d'un scan complet de table". Le reviewer senior n'a pas vu. La CI n'a pas vu. Staging n'a pas vu non plus, parce que staging était petit.

Donc j'ai construit le linter que je voulais : une GitHub Action qui lit chaque PR de migration et flag les commandes qui prennent un lock exclusif, suppriment des données, ou cassent la version déployée pendant le rollout. Quinze règles, tirées de postmortems réels, Squawk, ankane/strong_migrations, et la série Atlas PG301-311. Multi-ORM — Prisma, Drizzle, Rails, SQL brut.

C'est une GitHub Action gratuite. La détection est déterministe, pas LLM — un outil qui gate les merges et crie au loup se fait désactiver en une semaine.

→ migration.useautopilot.dev

Si t'as déjà shippé une migration qui a fait tomber la prod, c'était quoi le pattern ?
